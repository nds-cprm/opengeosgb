# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Idioma

Use **português do Brasil** em respostas, comentários, mensagens de commit e documentação deste projeto.

## O que é

OpenGeoSGB é a instância GeoNode do Serviço Geológico do Brasil (SGB/CPRM). Ele foi gerado a partir do template `geonode-project` e é um projeto Django fino (app `opengeosgb`, em `src/`) que estende o GeoNode 5 por meio de settings, templates, URLs e fixtures. Este é o repositório principal. Dependências e repositórios de referência:

- GeoNode do upstream, sem fork, instalado via `src/requirements.txt` a partir da tag `5.0.3` (`GeoNode @ git+https://github.com/GeoNode/geonode.git@5.0.3`). Personalizações são feitas por override neste projeto (settings, templates, handlers registrados no `ready()`), nunca alterando o pacote instalado. O código-fonte de referência fica em `<clones>/geonode` (ver "Clones de referência" abaixo).
- Apps extraídos do opengeosgb, publicados pela `nds-cprm` e instalados por tag no `src/requirements.txt`: `geonode-catalogue-iso19115-3` (catálogo CSW, ver "Catálogo CSW e ISO 19115-3") e `geonode-flatpages-editor` (ver "Flatpages"). Mudanças neles vão para o repositório de cada um, com tag nova.
- `<clones>/geonode-mapstore-client`: frontend (React/MapStore), uma dependência do GeoNode. Os templates sobrescritos ficam em `src/opengeosgb/templates/geonode-mapstore-client/`.
- `<clones>/geonode-project`: template de origem deste projeto, usado para comparar com a versão upstream, no branch da versão instalada (`5.0.x`). Sem clone, a skill `geonode-project` consulta o GitHub (`GeoNode/geonode-project`).
- `<clones>/documentation`: documentação do GeoNode, usada pela skill `geonode-architecture` para comparar a documentação com o código.
- `docker/`: submódulo git (`nds-cprm/geonode-docker`) com os Dockerfiles do nginx, GeoServer, PostGIS e letsencrypt, compartilhado com o geosdc. Acompanha o branch `unifica-opengeosgb`, que une os antigos `opengeosgb` e `geosdc` e vai substituir o `opengeosgb` quando tudo estiver pronto. O data dir do GeoServer é populado pela própria imagem `geoserver` no primeiro boot (não há mais `data-dir-conf`/`geoserver_data`). As versões vêm do `.env` (`NGINX_BASE_IMAGE_VERSION`, `GEOSERVER_BASE_IMAGE_VERSION`, `POSTGRES_BASE_IMAGE_VERSION`, `POSTGIS_BASE_IMAGE_VERSION`, `LETSENCRYPT_BASE_IMAGE_VERSION`), com valores de versão pura, usados como build arg e tag. Não use `GEOSERVER_VERSION`/`POSTGIS_VERSION` direto no `.env`: ele é `env_file` de todos os serviços e sobrescreveria variáveis homônimas das imagens.

**Clones de referência (`<clones>`).** O lugar dos clones muda conforme a máquina; confira qual existe antes de usar:
- `~/geonode-src/`: clones rasos que acompanham o `master`, criados pelas skills do plugin `geonode-assistant` (ver "Skills e agentes"). O script `test_stack.sh` da skill `geonode-rest-api` grava resultados em `~/geonode-src/test-results/`;
- a pasta-mãe do repositório (`../geonode`, `../geonode-mapstore-client`, `../geonode-project`): clones completos dos forks, com branches de trabalho (por exemplo `geonode-base-multistage` no core e `pt_BR-translation` no client). Não troque o branch deles sem perguntar; para ler outra versão, use `git show <ref>:<caminho>`.

Antes de comparar com o que está instalado, busque a versão certa, por exemplo `git -C <clones>/geonode fetch --depth 1 origin tag 5.0.3` (sem `--depth 1` nos clones completos) e depois `git -C <clones>/geonode show 5.0.3:<caminho>`. No client, use a tag com a versão de `django-geonode-mapstore-client` fixada no `requirements.txt` do GeoNode instalado (`5.0.3` para o GeoNode 5.0.3). O branch `5.0.x` traz as correções posteriores, ainda sem release.

## Comandos

O stack inteiro roda em contêineres, com Docker ou Podman. O compose base (`docker-compose.yml`) é sempre combinado com o override `docker-compose.opengeosgb.yml`, que monta `./src` em `/usr/src/project`, expõe as portas e constrói as imagens a partir do submódulo `docker/`:

```bash
git submodule update --init            # necessário para os builds do docker/
source opengeosgb-alias.sh             # define: geonode-docker = <compose> -f docker-compose.yml -f docker-compose.opengeosgb.yml
                                       # (Docker tem prioridade; force com CONTAINER_ENGINE=podman)
geonode-docker build
geonode-docker up -d
geonode-docker exec django python manage.py <cmd>
geonode-docker logs -f django celery
```

- Os serviços leem `.env` (`env_file`). Os arquivos `.env.dev`, `.env.prod`, `.env.p3m`, `.env.localhost` e `.env.restoreprod` são variantes por ambiente, e `.env.sample` é a referência das variáveis. Para gerar um `.env` novo: `python create-envfile.py --env_type dev|test|prod --hostname ...`.
- Backup e restore: o `docker-compose.opengeosgb.yml` monta `./draft/br` como `/backup_restore` nos serviços do Django, no lugar do volume `backup-restore` do compose base. Os scripts (`backup.sh`, `restore.sh`, `settings_docker.ini`) ficam em `src/opengeosgb/br/`.
- O container de dev pode ser aberto pelo `.devcontainer/` (serviço `django`, workspace `/usr/src/project`).
- A inicialização do container é feita por `src/entrypoint.sh` → `invoke` (`src/tasks.py`): `update`, `migrations`, `prepare` e `statics` em todo boot do django (o celery só roda o `update`). `fixtures`, `initialized` e `updateadmin` só rodam no primeiro boot (sem `/mnt/volumes/statics/geonode_init.lock`) ou com `FORCE_REINIT=true`. O `waitfordbs` está comentado. O task `fixtures` carrega os fixtures padrão do GeoNode e depois os listados em `PROJECT_FIXTURES`.

Lint: `flake8` com a configuração de `.flake8` (max-line-length 200; `F403`/`F405` ignorados por causa dos `import *` nos settings).

O projeto não tem suíte de testes própria. O `./opengeosgb-tests` roda os testes do GeoNode por grupo, como na CI do upstream, numa stack descartável `<COMPOSE_PROJECT_NAME>test` com as imagens já construídas pelo `geonode-docker build`. Os dados de teste vêm do código-fonte do commit do GeoNode instalado na imagem. Use `./opengeosgb-tests --help` para as opções, por exemplo `./opengeosgb-tests smoke`.

## Skills e agentes (plugin `geonode-assistant`)

Elas são genéricas: servem a qualquer GeoNode 3.2+ a 5.x, em inglês, português ou espanhol. Use-as, mas o que está neste arquivo prevalece sobre as receitas genéricas delas. Correções nas skills vão para o repositório do plugin, não para cá.

| Skill | Quando usar aqui | Ajustes ao opengeosgb |
|---|---|---|

| `geonode-mapstore-client` | `localConfig`, plugins, abas do painel, traduções do client | O projeto não compila o client: os ajustes são feitos em tempo de execução em `_geonode_config.html` e nos templates de `templates/geonode-mapstore-client/`. Compare com a tag `5.0.3` do client. |
| `geonode-architecture` | onde algo é implementado, comparação entre versões, documentação × código | Fixe a versão instalada (`5.0.3`) e indique se a comparação é com o `5.0.x` ou o `master`. |
| `geonode-rest-api` | chamadas à API v2, aprovação e publicação por `PATCH`, facets (`scale`) | Credenciais só por variáveis de ambiente (`GEONODE_URL`, `GEONODE_TOKEN` ou `GEONODE_USER`/`GEONODE_PASSWORD`). | `geonode-workflow-permissions` | aprovação, publicação, grupos e permissões | `ADMIN_MODERATE_UPLOADS` e `RESOURCE_PUBLISHING` vêm do `.env` (desligados no `.env.sample`); confira o valor do ambiente antes de diagnosticar. Agentes do plugin, acionados pelas skills ou diretamente:
- `geonode-code-explorer`: explora uma parte do core, do client ou da documentação e devolve um relatório com citações `arquivo:linha`. Usado pela `geonode-architecture` em paralelo, por exemplo para comparar `5.0.3` com o `master`;
- `geonode-log-triage` (Haiku): primeira passada em logs grandes, por serviço; extrai e anonimiza erros, sem diagnosticar;
- `geonode-log-analyzer`: diagnóstico a partir dos logs, com linha do tempo entre os serviços e até três hipóteses. Usado pela `geonode-debug-contrib`.

Os logs e o `.env` deste projeto têm dados reais: ao passá-los aos agentes, respeite "Cuidados" (nada de `secrets/`, `draft/` ou `.env.*`).

## Arquitetura

**Cadeia de settings.** `opengeosgb/settings.py` faz `from opengeosgb.local_settings import *`, e este faz `from geonode.settings import *`. Se o import de `local_settings` falhar com `ImportError`, ele cai direto em `geonode.settings`, sem aviso. Por isso, um pacote do `local_settings.py` ausente na imagem não aparece como erro de settings: o projeto sobe sem as customizações e quebra depois, por exemplo no import do `urls.py`. Logo, **toda customização de settings vai em `local_settings.py`**: flatpages e o editor, catálogo CSW, `LANGUAGES`, formulários de conta, provedores sociais, identificação/contato do pycsw, facets, traduções do client, o Google Tag Manager e o proxy reverso (`EXTERNAL_PROXY_ENABLED`). Já `settings.py` só cuida do que é estrutural do template (`STATICFILES_DIRS`, `LOCALE_PATHS` e `TEMPLATES` com prioridade para os diretórios locais, `ROOT_URLCONF`, `PROJECT_FIXTURES`). Quase tudo vem de variáveis de ambiente lidas pelo `geonode.settings`. O GeoNode 5.0.3 do upstream grava e serve metadados só em ISO 19139.

**Catálogo CSW e ISO 19115-3.** O formato ISO 19115-3 vem do app separado `geonode_catalogue_iso19115_3` (`nds-cprm/geonode-catalogue-iso19115-3`, extraído do opengeosgb), instalado pelo `src/requirements.txt` na tag `0.4.1`. Para atualizar, troque a tag e reconstrua a imagem. A configuração fica no `local_settings.py`:
- `CATALOGUE["default"]["ENGINE"]` aponta para o backend do app (variável `CATALOGUE_ENGINE`);
- `CATALOGUE_DEFAULT_FORMAT` (padrão `ISO19115-3_2018`; `ISO` volta ao ISO 19139) define o formato gravado no `metadata_xml`;
- `CATALOG_METADATA_TEMPLATE` é escolhido pelo formato entre `templates/opengeosgb/catalogue/full_metadata_iso19115-3.xml` e `full_metadata_iso19139.xml`. Eles estendem os templates do app e preenchem o bloco `spatial_resolution` com a escala. Por isso o aviso `geonode_catalogue_iso19115_3.W002` está em `SILENCED_SYSTEM_CHECKS`;
- o `GetDomain` do pycsw devolve a lista de valores com contagem (`domainquerytype = "list"`).

As rotas do app (`/catalogue/csw` e `/showmetadata/xsl/<pk>`) entram no início de `urlpatterns` em `urls.py`, antes das do GeoNode. O CSW só entrega o que o usuário pode ver e, além disso, só datasets e mapas aprovados e publicados: `PYCSW["FILTER"]` (no `local_settings.py`) é `{"resource_type__in": ["dataset", "map"], "is_approved": True, "is_published": True}`. A setting é do GeoNode, que só a aplica no `GetRecords`; a view do app a aplica também no `GetRecordById` e no `GetDomain`. Ela vale para todos os usuários, inclusive o admin, não afeta a geração do XML e substitui o padrão do GeoNode inteiro (só datasets). Por isso o CSW fica vazio enquanto nenhum recurso for aprovado e publicado. Depois de trocar o formato, regere e valide os XML: `python manage.py regenerate_metadata_xml --outdated` (use antes `--dry-run` para ver a lista) e `python manage.py validate_metadata_xml`. O comando é do app e cobre recursos de todos os tipos; o `regenerate_xml` do GeoNode só regera datasets. A referência completa das settings e dos comandos está no README do app.

**Configuração do client em tempo de execução.** `templates/geonode-mapstore-client/_geonode_config.html` (função `overrideLocalConfig`) ajusta o `localConfig.json` do client antes de ele ser usado:
- a coluna "Descrição" da lista do catálogo passa a ler `raw_abstract` (ver pendência [mapstore-client]);
- todas as datas configuradas (`type: "date"`) passam a usar o formato `L HH:mm`, a data numérica do idioma mais a hora em 24h (06/11/2026 23:42 em pt, 11/06/2026 23:42 em en).

A aba de informações do painel ganha a linha "Escala", depois de "Regiões" e só quando o recurso tem escala. Para isso:
- `opengeosgb/metadata/serializers.py` acrescenta o campo `scale` (o campo esparso) aos serializers de recursos do GeoNode (`ResourceBase`, `Dataset`, `Map`, `Document` e `GeoApp`) no `ready()` do app;
- o campo é diferido: só é calculado com `include[]=scale` ou com um preset que o inclua, por isso não pesa nas listagens;
- o `apps.py` o acrescenta ao preset `viewer_common`, usado pelo painel;
- o rótulo vem de `static/opengeosgb/translations/data.<locale>.json`, as traduções do client próprias do projeto, acrescentadas ao `MAPSTORE_TRANSLATIONS_PATH` em `local_settings.py`.

A barra de filtros do catálogo ganha o filtro "Escala", depois de "Região" (inserido pelo `overrideLocalConfig`). Ele é sustentado por `opengeosgb/metadata/facets.py`:
- `ScaleFacetProvider` é a facet `scale` da API `/api/v2/facets`, registrada em `FACET_PROVIDERS` no `local_settings.py`. Ela lista as escalas usadas e a contagem de recursos de cada uma.
- `ScaleFilter` filtra a API de recursos pelo parâmetro `scale=<denominador>`, que pode se repetir. O `apps.py` o acrescenta ao `ResourceBaseViewSet.filter_backends`, e a API de facets usa esse mesmo filtro nas contagens.

O filtro padrão do `dynamic_rest` (`filter{…}`) não funciona para campos esparsos, por isso o parâmetro próprio.

O painel de propriedades (`ResourceDetails`) não mescla configuração parcial. Por isso, nas páginas sem `cfg.tabs`, o override fornece as abas completas a partir de `templates/opengeosgb/resource_details_tabs.json`, uma cópia das abas padrão do client 5.0.3 extraída de `resource-details-plugin.*.chunk.js`. **Ao atualizar o geonode-mapstore-client, compare esse JSON com o padrão da nova versão.**

**Sobrescrita de templates.** `src/opengeosgb/templates/` vem primeiro em `TEMPLATES[0]["DIRS"]` (o `apps.py` também o insere no `ready()`). Para customizar uma página, crie um arquivo com o mesmo caminho relativo do template original do GeoNode ou do mapstore-client (por exemplo `geonode-mapstore-client/snippets/hero.html` ou `geonode_base.html`). Os arquivos estáticos seguem a mesma lógica com `src/opengeosgb/static/`. Ajustes de CSS sobre o tema do client ficam em `static/opengeosgb/css/opengeosgb.css`, carregado no `head.html` do client. Hoje esse arquivo tem só o título dos cards do catálogo, com até duas linhas e altura fixa de duas linhas. Use seletores mais específicos que os do tema (prefixo `.msgapi`), porque o tema do client pode ser carregado depois.

**URLs.** `opengeosgb/urls.py` importa `geonode.urls.urlpatterns` e acrescenta as rotas próprias: flatpages em `/pages/` e a rota legada do GeoNode 4 `datasets/<alternate>/metadata_detail`, que redireciona (301) para `metadata/<pk>` (`views.legacy_metadata_detail`). Ela existe para manter vivos os links antigos do P3M. A rota `showmetadata/xsl/<pk>` do link "ISO with XSL", que o GeoNode cria em datasets e documentos, também redireciona (302) para `metadata/<pk>`. O redirecionamento vem do app `geonode_catalogue_iso19115_3` e só vale com o formato ISO 19115-3: o `metadata.xsl` do GeoNode só entende ISO 19139, e o Chrome deixou de executar XSLT a partir de 17/11/2026. O destino é a rota de nome `metadata` (padrão da setting `CATALOGUE_XSL_REDIRECT` do app, que o opengeosgb não altera), e o opengeosgb sobrescreve essa rota com a página própria.

**Autenticação.** Os formulários do allauth são trocados por `opengeosgb.account.forms` (variantes GovBR, com ou sem reCAPTCHA conforme `RECAPTCHA_ENABLED`). Os provedores sociais são Google, ORCID e OpenID Connect (gov.br). O `GovBRExtractor` (`account/profileextractors.py`) mapeia os claims do gov.br para o perfil do usuário.

**Context processors.** `opengeosgb.context_processors.google_tag_manager_snippet` expõe `GOOGLE_TAG_MANAGER_ID` aos templates, mas só quando o valor casa com `^GTM-[A-Z0-9]{4,10}$`. `site_pages` expõe `COOKIE_POLICY_URL` e `ABOUT_PAGE_URL` no idioma da requisição. Esses endereços são usados no aviso de cookies e no rodapé (`templates/geonode-mapstore-client/snippets/footer.html`, cópia do snippet do client 5.0.3). O rodapé tem os links Sobre, Política de cookies e Preferências de cookies, este último reabrindo o aviso. O `ABOUT_PAGE_URLS` segue o mesmo padrão descrito a seguir para a política de cookies. O valor vem de `COOKIE_POLICY_URLS` (em `local_settings.py`), que mapeia `pt` para `/pages/politica-de-cookies/` e `en` para `/pages/cookie-policy/`. Os dois endereços são configuráveis por `COOKIE_POLICY_URL` e `COOKIE_POLICY_URL_EN`. Flatpages não têm tradução: cada idioma é uma página separada, com um link no topo para a outra versão (`/pages/sobre/` e `/pages/about/`, `/pages/politica-de-cookies/` e `/pages/cookie-policy/`).

**Aviso de cookies (LGPD) e Google Tag Manager.** `templates/opengeosgb/snippets/cookie_consent.html` é incluído no `<head>` de `templates/base.html` (páginas do Django) e de `templates/geonode-mapstore-client/snippets/head.html` (páginas do client). Ele roda uma única vez por página, mesmo quando incluído nos dois.
- Mostra uma faixa no rodapé com "Rejeitar cookies opcionais", "Aceitar cookies" e o link para a política. A faixa fica num `<template>` e é inserida no `<body>` por JavaScript.
- A escolha fica no cookie `opengeosgb_cookie_consent` (`accepted` ou `rejected`, 1 ano).
- **O Google Tag Manager só é carregado depois do aceite**, por isso não existe mais snippet de GTM carregado diretamente. Ao recusar, os cookies `_ga`, `_gid`, `_gat` e `_gcl` são apagados.
- Qualquer link para `#preferencias-de-cookies` reabre a faixa. A página de política usa esse link, e ele é aceito pela sanitização das flatpages.
- Para atender ao LGPD, o `<noscript>` do GTM não é usado: sem JavaScript não há como registrar consentimento.

**Fixtures do projeto.** `src/fixtures/opengeosgb/` contém licenças e regiões do Brasil, além do tesauro `labels-i18n.rdf` (rótulos pt do editor de metadados do GeoNode: títulos e descrições dos campos como sobrescritas `<campo>__ovr`/`<campo>__descr__ovr`, e mensagens `metadata_*` do editor). Ele não é carregado automaticamente; para carregar ou atualizar em um ambiente:

```bash
geonode-docker exec django python manage.py thesaurus load -i labels-i18n \
  -f /usr/src/project/fixtures/opengeosgb/labels-i18n.rdf --action update   # use --action create na primeira carga
```

O editor guarda os rótulos em cache, mas invalida o cache sozinho quando o tesauro muda, então não é preciso reiniciar.

O arquivo `opengeosgb-flatpages.json` traz as flatpages institucionais: Sobre/About e Política de cookies/Cookie policy, ids 10 a 13. Os ids são fixos porque os endereços das imagens (`/uploaded/flatpages/<id>/…`) dependem deles. Carregar o fixture sobrescreve flatpages que já tenham esses ids. As páginas Sobre (10) e About (12) ainda têm o texto de exemplo do editor e usam as imagens `/uploaded/flatpages/10/faixas-geologicas.png` e `/uploaded/flatpages/12/geological-bands.png`, que deveriam estar em `flatpages_media/<id>/`. Essa pasta nunca foi versionada, então o `cp` abaixo falha e as imagens só existem onde foram enviadas (ver pendência). Para carregar em um ambiente:

```bash
geonode-docker exec django python manage.py loaddata /usr/src/project/fixtures/opengeosgb/opengeosgb-flatpages.json
geonode-docker exec django bash -c 'mkdir -p /mnt/volumes/statics/uploaded/flatpages && cp -r /usr/src/project/fixtures/opengeosgb/flatpages_media/* /mnt/volumes/statics/uploaded/flatpages/'
```

Para regerar o fixture depois de editar as páginas: `python manage.py dumpdata flatpages.flatpage --pks 10,11,12,13 --indent 2`, copiando também as pastas `uploaded/flatpages/10` e `12` para `flatpages_media/`.

O `opengeosgb-legacy-menu.json` (seção "Serviços legados do GeoSGB" da home) está comentado em `PROJECT_FIXTURES`, no `settings.py`, e não é carregado.

**Handler de metadados do projeto.** `opengeosgb/metadata/handlers.py` define o `OptionsI18nHandler`, registrado no `ready()` do app (`apps.py`) via `metadata_manager.add_handler()`. Ele roda depois dos handlers do GeoNode e não é dono de nenhum campo. Sua função é traduzir, com `pgettext` e um contexto por campo, as opções que o GeoNode monta sem `gettext`: idioma, restrições e tipo de representação espacial. As traduções ficam no `django.po`, em uma seção própria com `msgctxt`. No mesmo `ready()`, o handler `region` do GeoNode é substituído por `RegionsI18nHandler`, que aponta o campo de regiões para o autocomplete próprio (`opengeosgb/metadata/views.py`, rota `opengeosgb_metadata_autocomplete_regions`) e traduz os rótulos das regiões salvas. Só regiões de nível 0 a 3 (global, continentes, sub-regiões e países) são traduzidas, com o contexto `metadata region`. Os estados (nível 4) e municípios (nível 5) brasileiros já estão em português e ficam fora do `.po`. A regra está em `opengeosgb/metadata/i18n.py`. O handler `base` também é substituído, por `BaseFormHandler`, que muda duas coisas no formulário. O campo "date" passa a ser editado só como data, e ao salvar o horário já gravado é mantido. O campo "supplemental_information" deixa de ter texto padrão. Quando o editor manda esse campo nulo ou ausente, ele é gravado como texto vazio, porque a coluna é `NOT NULL` no GeoNode. Tornar o campo nulo de verdade exige mudar o modelo no GeoNode (upstream).

**Campos extras do editor.** Campos que não existem no `ResourceBase` são declarados em `opengeosgb/metadata/fields.py`. Hoje só existe `scale`, opcional. Ele é um objeto `{id: denominador, label: "1:250.000"}`, porque o editor só oferece autocomplete para objetos e listas. As sugestões vêm de `opengeosgb/metadata/scales.py`: as escalas comuns de `COMMON_SCALES` mais as já usadas em outros recursos. O que o usuário digita também vira opção, o que substitui o `creatable`, que o client não suporta em seleção única. O `SparseFieldsUiHandler` liga o autocomplete ao campo e apaga o `{}` que o GeoNode grava quando o campo é limpo. Eles são registrados como campos esparsos do GeoNode (`sparse_field_registry`, tabela `SparseField`) no `ready()` do app, sem precisar de migração. Os rótulos em português vão no tesauro `labels-i18n` (`<campo>__ovr` e `<campo>__descr__ovr`), que precisa ser recarregado com `--action update` depois de mudanças. Campos esparsos não saem sozinhos no XML ISO/CSW: o template de metadados precisa usá-los via `metadata.<campo>`, contexto que o `csw_gen_xml` já fornece. Hoje só a escala sai, em `spatialResolution/MD_Resolution/equivalentScale` (`mri:` no ISO 19115-3, `gmd:` no ISO 19139), pelos templates `templates/opengeosgb/catalogue/full_metadata_*.xml`, que estendem os do app `geonode_catalogue_iso19115_3` (ver "Catálogo CSW e ISO 19115-3"). O XML de recursos existentes só é regerado pelo `regenerate_metadata_xml` do app (ou pelo `regenerate_xml` do GeoNode, que só cobre datasets) ou quando o recurso passa pelo `catalogue_post_save`, que roda no save de `Dataset` e `Document`. No GeoNode 5.0.3, salvar pelo editor de metadados não regera o XML: o editor salva o `ResourceBase` sem polimorfismo (`ResourceBaseManager` usa `non_polymorphic()`), e o sinal não dispara.

**Página de visualização de metadados.** As rotas `/metadata/<pk>` e `/metadata/<pk>/embed` (a segunda é usada em iframe pelo plugin `MetadataViewer` do client) foram substituídas pelas views de `opengeosgb/metadata/views.py`. Elas são inseridas no início de `urlpatterns` em `urls.py` e mantêm os mesmos nomes de rota. Diferente da view original do client, verificam a permissão de leitura do recurso (`base.view_resourcebase`). O conteúdo é montado em `opengeosgb/metadata/page.py`:
- seções fixas (`SECTIONS`); campos preenchidos que não estão em nenhuma seção vão para "Outras informações";
- extensão geográfica e sistema de referência;
- contatos agrupados por pessoa;
- dicionário de dados (atributos do dataset);
- citação;
- links de distribuição agrupados;
- registro de metadados.

Na distribuição, os arquivos originais (assets do upload) ficam separados dos downloads gerados pelo GeoServer. O link de GeoPackage não é criado pelo GeoNode: a página monta esse link a partir do download WFS em CSV, trocando o `outputFormat` para `geopkg`. Isso depende das extensões `excel` e `geopkg-output` do GeoServer, instaladas pelo `ARG GEOSERVER_EXTENSIONS` no Dockerfile do submódulo `docker/docker/geoserver`. Datas são formatadas no Python, no formato curto do idioma ativo. A apresentação fica no snippet sobrescrito `templates/geonode-mapstore-client/snippets/metadata_view.html`, usado pelos dois templates do client, mais `templates/opengeosgb/snippets/metadata_item.html`. Os títulos dos campos vêm do schema, já traduzidos, e por isso não passam por `{% trans %}`. Passar causaria tradução dupla: "Data" virava "Dados".

**Flatpages (pacote `geonode-flatpages-editor`).** O editor das flatpages vem do pacote [`nds-cprm/geonode-flatpages-editor`](https://github.com/nds-cprm/geonode-flatpages-editor), extraído do antigo app `opengeosgb.flatpages_editor` e instalado pelo `src/requirements.txt` (tag `v0.2.0`). O app `geonode_flatpages_editor` entra no `INSTALLED_APPS` pelo `local_settings.py`, logo depois de `django.contrib.flatpages`, porque substitui o admin dele (o check `flatpages_editor.E002` acusa a ordem errada). No admin, o conteúdo é editado com o TinyMCE 5 do `django-tinymce` do GeoNode, restrito a texto, títulos h2 a h6, listas, citação, links (`http`, `https`, `mailto`, `tel` e âncoras, como `#preferencias-de-cookies`), imagens e tabelas só com estrutura. O HTML é sanitizado com `bleach` ao salvar e de novo ao exibir (filtro `sanitize_flatpage`). A rota `pages/`, que publica as flatpages, e o sitemap continuam no `urls.py` do projeto.

O upload de imagens fica no próprio admin (`/admin/flatpages/flatpage/upload-image/`, rota `admin:flatpages_flatpage_upload_image`). Ele aceita só membros da equipe com permissão de adicionar ou alterar flatpages, exige o token CSRF e valida a imagem com o Pillow (PNG, JPEG, GIF ou WebP, até 5 MB). As imagens são gravadas por página, em `MEDIA_ROOT/flatpages/<id_da_página>/<nome>.<ext>`, e servidas em `/uploaded/flatpages/<id>/…`. Numa página ainda não salva, o upload vai para `flatpages/tmp/<uuid>/` e é movido para a pasta da página ao salvá-la. Quando a página é apagada, a pasta dela é apagada junto.

As imagens órfãs (de páginas novas não salvas, removidas do conteúdo ou de páginas excluídas fora do admin) são apagadas pela tarefa `geonode_flatpages_editor.cleanup_orphan_images`, agendada no `CELERY_BEAT_SCHEDULE` do `local_settings.py` todo dia às 3h, na fila `cleanup`. A fila precisa ser explícita: a tarefa não define fila, e o worker do GeoNode só consome as de `CELERY_TASK_QUEUES`. Só são apagadas imagens que nenhuma página usa e com mais de 24 horas. Para rodar à mão: `python manage.py flatpages_cleanup_images [--dry-run] [--min-age <horas>]`.

**Imagem Docker.** O `Dockerfile` parte de `docker.io/ndscprm/geonode-base:ubuntu-24.04-pg${POSTGRES_CLIENT_VERSION}` (build arg `GEONODE_BASE_IMAGE`; com o sufixo `-devel`, usa a variante com compiladores). Há uma variante por versão major do PostgreSQL (hoje `pg15` e `pg17`), escolhida pelo build arg `POSTGRES_CLIENT_VERSION` (padrão `17`). O `docker-compose.opengeosgb.yml` o preenche com o `POSTGRES_BASE_IMAGE_VERSION` do `.env`, a mesma variável que define a imagem do postgis. É a base do GeoNode 5.0.x em multi-stage (`docker/base/ubuntu/multi-stage/Dockerfile` do `nds-cprm/geonode`, branch `geonode-base-multistage`): Ubuntu 24.04 com o GDAL 3.8.4 do apt, venv em `/usr/src/venv` e, sem compiladores, os pacotes do GeoNode 5.0.x sem wheel para Python 3.12 já compilados nas versões fixadas (GDAL 3.8.4, psycopg2 2.9.12, pylibmc 1.6.3, uWSGI 2.0.30). O estágio `devel` (a mesma imagem mais os compiladores e os pacotes `-dev`) é publicado com o sufixo `-devel` (por exemplo `ubuntu-24.04-pg17-devel`).

O Dockerfile do projeto instala `src/requirements.txt` (GeoNode 5.0.3 do upstream) numa camada própria, antes de copiar `src/`, e depois faz `pip install -e .`. Pacotes novos precisam ter wheel ou ser Python puro. Logo depois do `requirements.txt`, numa camada própria, instala com `--no-deps` as versões de `src/requirements-overrides.txt`, que substituem versões fixadas pelo GeoNode por correções de segurança. Hoje só o `Pillow==13.0.0`: o GeoNode 5.0.3 fixa `Pillow==12.1.1`, afetado por dezenas de vulnerabilidades, e o upstream só passou para o 13.0.0 nos branches `5.1.x` e `master`. O build termina com o `src/build-smoke-test.sh`, que roda o `geonode-base-smoke-test` da base. O smoke test falha se os pacotes do projeto trocarem as versões compiladas na base (GDAL, psycopg2, pylibmc, uWSGI) ou deixarem dependências quebradas (`pip check`). O script aceita a falha do `pip check` só quando todas as linhas vêm das versões de `requirements-overrides.txt`; qualquer outra falha derruba o build. Ao atualizar o GeoNode, remova do arquivo as linhas que o GeoNode novo já cobre. O que a base já traz não é repetido no Dockerfile do projeto: curl, wget, unzip, gnupg2, o venv com pip/setuptools/wheel e o `invoke`. A base não define locale, por isso o projeto define `LC_ALL`/`LANG=C.UTF-8`; esse locale já vem na glibc do Ubuntu 24.04. Ao mudar a versão do GeoNode, atualize `src/requirements.txt` e reconstrua a imagem. O Dockerfile só copia `src/`. Por isso o `.dockerignore` deixa de fora do contexto de build `draft/`, `secrets/`, `.env*`, `.git/`, `docker/` e `venv/`. Sem essas exclusões, o build mandava cerca de 2 GB, incluindo backups de produção, ao daemon ou à máquina do Podman.

**Proxy externo (HAProxy em `mode http`).** O nginx do submódulo (`docker/docker/nginx/`) pode ficar atrás de um load balancer, que termina o TLS público. Com todas as variáveis abaixo vazias, o nginx é a borda, como antes. O `docker-entrypoint.sh` gera a configuração a cada boot:
- `PUBLIC_SCHEME` e `PUBLIC_PORT` definem a URL pública (`PUBLIC_HOST`, `HTTP_SCHEME`) usada nos cabeçalhos `Host`, `Origin` e `X-Forwarded-*` e nos redirecionamentos. Sem elas, o esquema vem de `HTTPS_HOST` e a porta de `HTTP_PORT`/`HTTPS_PORT`. Com `PUBLIC_SCHEME=https` e sem `PUBLIC_PORT`, vale a 443, e a porta publicada para o load balancer não aparece no endereço.
- `PROXY_TRUSTED_ADDRESSES` (IPs ou CIDRs, sem nomes de host) gera o `/etc/nginx/realip.conf`, que não fica no repositório: `set_real_ip_from` mais `real_ip_header X-Forwarded-For` (ou `PROXY_REAL_IP_HEADER`) e `real_ip_recursive on`. Só dos endereços confiáveis o `X-Forwarded-For` muda o `$remote_addr`. Use os IPs exatos dos HAProxy, do jeito que o container os enxerga: com NAT nas portas publicadas, pode ser o gateway da rede do Docker.
- O nginx sempre manda ao Django e ao GeoServer `X-Forwarded-For $remote_addr`, um único IP já validado, e não `$proxy_add_x_forwarded_for`. O GeoNode usa o primeiro item do cabeçalho (`get_client_ip`, inclusive no `AUTH_IP_WHITELIST`), e antes esse item podia ser forjado pelo cliente.
- `NGINX_EXTRA_SERVER_NAMES` aceita nomes extras no `server_name`, só para um load balancer que não preserve o `Host`. Sem isso, o `default_server` responde 444.
- O GeoServer 2.28 só aceita o `X-Forwarded-For` de proxies listados em `GEOSERVER_TRUSTED_PROXIES` (IPs ou CIDRs, `RemoteIpFilter`); sem ele, trata o nginx como o cliente (aviso "not a trusted proxy" no log). Se a variável não estiver definida, o entrypoint da imagem a preenche com o loopback e as sub-redes IPv4 das redes do container, onde estão as réplicas do nginx (ele é escalável, por isso não se fixa o IP dele). Definida, ela aceita IPs, CIDRs e nomes de host, que o entrypoint resolve no boot (`getent`, todos os endereços), porque o GeoServer só aceita IPs e CIDRs. O nome tem até `GEOSERVER_TRUSTED_PROXIES_WAIT` segundos (padrão 60) para resolver, senão fica de fora com um aviso. A resolução só vale até o GeoServer reiniciar: um proxy recriado com outro IP, ou uma réplica nova, fica de fora. Os IPs do HAProxy não entram nela: quem confia no HAProxy é o nginx (`PROXY_TRUSTED_ADDRESSES`), que repassa um único IP já resolvido.
  - Riscos de confiar na sub-rede: qualquer container da mesma rede pode forjar o `X-Forwarded-For` direto na 8080. Isso afeta o IP que o GeoServer registra e as regras do GeoFence por IP, não a autenticação.
  - A sub-rede inclui o gateway. Testado em 26/11/2026: quem chega pela porta 8080 publicada pelo gateway (o próprio host no Docker; conforme o motor, como Docker ou Podman sem root, também clientes externos) é confiável. Por isso o `docker-compose.opengeosgb.yml` não publica a 8080 (`ports: !reset []`, que apaga a porta do compose base; a tag exige Docker Compose 2.24+). O acesso externo ao GeoServer passa pelo nginx (`/geoserver/`). Só o devcontainer, que é ambiente de desenvolvimento, publica a 8080. Não use faixas privadas largas (`10.0.0.0/8`).
  - No Kubernetes, o equivalente é o CIDR dos pods com uma NetworkPolicy que só deixe o nginx, o Django e o Celery chegarem à 8080. Isso exige:
    - um CNI que aplique a política;
    - Service só do tipo ClusterIP, já que NodePort e LoadBalancer fazem SNAT para um endereço que pode cair no CIDR;
    - default-deny no namespace.
- Para o nginx também fazer TLS sob o load balancer (reencriptação), preencha `HTTPS_HOST`, use `LETSENCRYPT_MODE=disabled` e aponte o HAProxy para a porta do `HTTPS_PORT`. O certificado autoemitido tem CN e SAN com `HTTPS_HOST` e serve para `verify required`, mas é refeito no boot depois de 365 dias. Um certificado da AC interna em `<LETSENCRYPT_MODE>/live/<HTTPS_HOST>/{fullchain,privkey}.pem`, no volume `nginx-certificates`, tem prioridade. O nginx só aceita TLS 1.2 e 1.3.

No Django, `EXTERNAL_PROXY_ENABLED=True` (no `local_settings.py`) define `SECURE_PROXY_SSL_HEADER`, para o Django confiar no `X-Forwarded-Proto` que o nginx sempre sobrescreve. Com o uWSGI do stack (`http-socket`), o POST funciona mesmo sem ela, porque o próprio uWSGI define o esquema da requisição pelo `X-Forwarded-Proto`: testado direto na porta 8000, o login passa com `X-Forwarded-Proto: https` e falha com 403 "Origin checking failed" sem o cabeçalho. Ela continua necessária fora do uWSGI (por exemplo, `runserver` no devcontainer) e deixa explícita a confiança no cabeçalho, também quando o próprio nginx faz o TLS. Ela só é segura se a porta 8000 do Django não for acessível sem passar pelo nginx. Deixe `SECURE_SSL_REDIRECT=False`, porque quem redireciona para https é o load balancer. Exemplo de `.env`:

```dotenv
HTTP_HOST=geoportal.sgb.gov.br
HTTPS_HOST=                     # ou o mesmo nome, se o nginx também fizer TLS
PUBLIC_SCHEME=https
PROXY_TRUSTED_ADDRESSES=<IPs dos HAProxy>
EXTERNAL_PROXY_ENABLED=True
SITEURL=https://geoportal.sgb.gov.br/
```

No HAProxy: `option forwardfor`, `Host` preservado (padrão), redirecionamento para https e `timeout client/server` de 600 s (os do nginx). O PROXY protocol não é usado: em `mode http` o `X-Forwarded-For` basta, e ele exigiria portas separadas no nginx. As URLs que o GeoServer e o GeoNode publicam não vêm do nginx, e sim do `.env`, que precisa ter todas em `https://` com o nome público:
- `SITEURL` e `NGINX_BASE_URL`;
- `GEOSERVER_PUBLIC_LOCATION` e `GEOSERVER_WEB_UI_LOCATION`;
- o `-DPRINT_BASE_URL` dentro de `GEOSERVER_JAVA_OPTS`.

O entrypoint da imagem do GeoServer (`docker/docker/geoserver/scripts/entrypoint.sh` e `set_geoserver_auth.sh`) regrava o `proxyBaseUrl` do `global.xml` a cada boot. Ele troca o esquema e o host do valor atual pelo `NGINX_BASE_URL` (ou pelo `SITEURL`, se o primeiro estiver vazio) e mantém o caminho `/geoserver`. Com https, isso dá `https://<host>/geoserver`. É esse valor que sai no GetCapabilities e nos links de legenda. Se ficar em `http://`, o navegador bloqueia essas URLs como conteúdo misto. O `useHeadersProxyURL` não é usado: a URL é fixa. O CSRF da interface web do GeoServer está desligado (`-DGEOSERVER_CSRF_DISABLED=true` no `GEOSERVER_JAVA_OPTS`), por isso a diferença de domínio não afeta o login dela. Num ambiente que já existia em `http://`, as URLs gravadas no banco (links OWS e miniaturas) não mudam sozinhas. Troque-as com `python manage.py migrate_baseurl --source-address=http://<host> --target-address=https://<host>`, do GeoNode, que atualiza `Link`, miniaturas e estilos. Em 26/11/2026, a configuração foi testada com um HAProxy descartável na rede do compose, nos dois modos (nginx em HTTP e em TLS com `verify required`): páginas, estáticos, GeoServer, API, redirecionamentos em https, IP real com descarte de cabeçalho forjado, e o POST do login com e sem `EXTERNAL_PROXY_ENABLED`. O teste foi repetido no mesmo dia com o stack sem root e somente leitura, e passou nos dois modos; o GeoServer também registrou o IP real do cliente (API do módulo de monitoramento). O POST do login passou também sem `EXTERNAL_PROXY_ENABLED`, por causa do uWSGI (ver acima).

**Sem root e com filesystem somente leitura.** No `docker-compose.opengeosgb.yml`, todos os serviços ativos rodam sem root e com `read_only: true`. Eles só gravam nos volumes e em tmpfs:
- django e celery: `1000:0`, com `HOME=/tmp`. Os logs do uWSGI/Django e do Celery vão para stdout/stderr (`geonode-docker logs`), sem arquivo: o `uwsgi.ini` não tem `logto`, e o `celery-cmd` só passa `-f` quando `CELERY__LOG_FILE`/`CELERY__BEAT_LOG` estão definidos. O `celerybeat-schedule` fica no volume statics, junto do statedb do worker;
- geoserver: `1000:0`, sem porta publicada (ver "Proxy externo"). Usa tmpfs em `temp` (com `exec`, por causa das bibliotecas nativas extraídas pelos jars), em `work` e em `logs` (256 MB). O log do GeoServer sai em stdout pelo "Log to StdOut" da página "Global" da interface web (`<stdOutLogging>` do `logging.xml`), que o entrypoint liga a cada boot. O perfil de log continua configurável na interface, e o GeoServer continua gravando o `logs/geoserver.log` do data dir (até 3 arquivos de 20 MB). Os logs do Tomcat usam a configuração da imagem base: o conteúdo do JULI já sai no console (`ConsoleHandler`), e os arquivos ficam no tmpfs de `logs`, perdidos a cada reinício (com o tmpfs cheio, só os arquivos param). O access log do Tomcat vai para stdout: a imagem aponta o `AccessLogValve` do `server.xml` para `/dev/stdout`, sem rotação nem buffer. O `-XX:LogFile` do `GEOSERVER_JAVA_OPTS` precisa apontar para um volume gravável, como o `/tmp/jvm.log` do `.env.sample`;
- nginx: `101:0`, com tmpfs de 64 MB em `/tmp`. O entrypoint gera a configuração em `/tmp/nginx`, e o `/etc/nginx/nginx.conf` da imagem é um link para lá. Os temporários de resposta (`proxy_temp_path`) ficam fora do tmpfs, que ocupa RAM: vão para `/var/cache/nginx`, um volume anônimo em disco por container. Antes, um download lento de 500 MB ocupava 500 MB do tmpfs.
  - Com o temporário, o nginx lê a resposta do Django ou do GeoServer sem esperar o cliente e libera o worker do uWSGI. Sem ele, cada download prende um worker pelo tempo do cliente, e o `harakiri = 600` corta os downloads com mais de 10 minutos.
  - `NGINX_PROXY_MAX_TEMP_FILE_SIZE` (padrão `2048m`) limita o temporário de cada resposta; acima dele, o nginx repassa no ritmo do cliente. Dimensione o disco do host do nginx: N downloads lentos ocupam até N × esse valor, e com o disco cheio os downloads falham.
  - `NGINX_DOWNLOADS_PER_IP` (padrão 8; `0` desliga) limita os downloads simultâneos por IP nas rotas de arquivo do Django: `/api/v2/assets/<id>/download`, `/documents/<id>/download` e `/link`, `/datasets/<nome>/dataset_download`. Acima do limite, o nginx responde 429. Atrás de proxy externo, depende do `PROXY_TRUSTED_ADDRESSES`; sem ele, todos os clientes dividem o limite do IP do proxy.
  - Testado em 27/11/2026 com quatro anexos diferentes de 424 MB, baixados a 2 MB/s:
    - com 32 downloads simultâneos, o worker ficou preso em média 11 s com o temporário, contra 25 s (o tempo todo do cliente) sem ele;
    - com 130 downloads sem o temporário e sem o limite, os 128 workers lotaram e a home chegou a 24 s; com o limite de 8, foram 122 respostas 429 e a home não passou de 0,17 s;
    - `aio threads` não ajudou e ficou de fora.
  - Downloads de 2 GB, testados um a um, conferiram o hash. Os uploads não passam pelo tmpfs (`proxy_request_buffering off`): 2 GB enviados ao GeoServer pelo nginx, com e sem chunked, não ocuparam o `/tmp`. Na rota do Django, com o limite do GeoNode aumentado só para o teste (`UploadSizeLimit`), 2 GB passaram pelo nginx em 12 s, também sem ocupar o `/tmp`. O caminho completo também foi testado com um GeoTIFF real de 1,68 GB (20000×20000, RGB, com overviews), sem ocupar o `/tmp`: upload pelo importador, publicação, download do original (zip, conferido byte a byte), WMS e recorte pelo WCS. O WCS do raster inteiro, que é o link "GeoTIFF" do GeoNode, falha por causa do limite de leitura do WCS no GeoServer (cerca de 586 MB). O importador deixa a cópia do upload em `uploaded/tmp*/`, mesmo depois de o recurso ser apagado. A rota do Django usa `proxy_buffers 8 16k` (padrão 4/8 KB). Com isso, o download pelo nginx foi de cerca de 545 para 760 MB/s, perto dos 800 MB/s direto no uWSGI. No `/geoserver` ficou o padrão, porque buffers maiores deixaram o download do GeoServer cerca de 12% mais lento. Os uploads ficam iguais pelo nginx e direto. Upload chunked (sem `Content-Length`) não funciona no Django, nem direto no uWSGI: ele recebe o corpo vazio. Um arquivo só de zeros deixa o parser multipart do Django em cerca de 1,3 MB/s, com 100% de CPU, até o `harakiri`; para testar upload, use dados aleatórios. Se algum upload fosse bufferizado, falharia ao encher os 64 MB, sem esgotar a memória;
- db (`postgres`, 70) e redis (`redis`, 999), donos dos volumes de dados. O entrypoint pula o `chown`, então um volume criado com outro dono precisa de `chown` antes. O db usa tmpfs em `/run/postgresql` e `/tmp`;
- memcached (`memcache`, da imagem) e mailserver (`nobody`).

Os logs dos containers (`geonode-docker logs`) têm rotação em todos os serviços, pela âncora `x-logging` do `docker-compose.opengeosgb.yml`: até 5 arquivos de 10 MB por container (`max-size`/`max-file`). Só vale para containers recriados. O letsencrypt continua como root, porque o crond precisa dele. O devcontainer desliga o `read_only` do django, porque o VS Code Server se instala em `/home/ubuntu`. Para achar o que um serviço grava fora dos volumes, rode `docker diff <container>` com ele fora do modo somente leitura.

**Arquitetura (amd64 e arm64).** O stack roda na arquitetura nativa do host, seja amd64 (Linux x86_64) ou arm64 (por exemplo, Mac com Apple Silicon e Podman). Confira com `uname -m` antes de seguir instruções que dependam dela. O `docker-compose.opengeosgb.yml` não define `platform` nem `TARGETPLATFORM`. Assim, o `FROM --platform=$TARGETPLATFORM` dos Dockerfiles do `docker/` e as imagens do compose base (redis, memcached, mailserver) usam a arquitetura nativa. Para forçar outra arquitetura num serviço, passe `TARGETPLATFORM=linux/<arch>` nos args do build e `platform` no serviço. Todas as bases usadas são publicadas para amd64 e arm64, exceto a do postgis. A imagem oficial `postgis/postgis` só existe para amd64. Por isso, o serviço `db` passa `POSTGIS_BASE_IMAGE=docker.io/imresamu/postgis:<pg>-<postgis>-alpine3.22`, uma build multiarquitetura da mesma imagem, ao `docker/docker/postgis/Dockerfile`. Sem esse arg, ele cai na `postgis/postgis`. Um volume `dbdata` do PG 17 criado em amd64 abriu sem problema no postgis arm64: em 23/11/2026, a leitura completa das tabelas e o `bt_index_check` de todos os índices btree não acusaram erro. Mesmo assim, copie o volume antes de trocar a arquitetura. Se uma imagem já baixada estiver na arquitetura errada, baixe-a de novo com `podman pull --platform linux/<arch> <imagem>` (ou `docker pull`), com a arquitetura do host. Um `podman run --platform linux/amd64` com uma tag local também pode substituir essa tag pela versão do Docker Hub. Nesse caso, rode `geonode-docker build <serviço>` de novo.

**Banco de dados (PostgreSQL 17).** O padrão do projeto é `POSTGRES_BASE_IMAGE_VERSION=17` (postgis `17-3.4`, sobre `imresamu/postgis:17-3.4-alpine3.22`). A versão major precisa ser a mesma que inicializou o volume `<COMPOSE_PROJECT_NAME>-dbdata`. Se não for, o container `db` reinicia em loop com `database files are incompatible with server` (`initialized by PostgreSQL version 15`). Volumes antigos, criados com a imagem `geonode/postgis:15-3.5-latest`, estão no PG 15. Para migrar um desses volumes para o 17, use dump e restore (exemplo com Podman; com Docker os comandos são os mesmos):

```bash
P=<COMPOSE_PROJECT_NAME>
# 1. cópia de segurança do volume
podman volume create $P-dbdata-pg15-backup
podman run --rm -v $P-dbdata:/from:ro -v $P-dbdata-pg15-backup:/to alpine cp -a /from/. /to/
# 2. dump com um PostgreSQL 15 temporário sobre o volume; o arquivo fica no volume dbbackups.
#    A geonode/postgis:15-3.5-latest só existe para amd64 (nativa em amd64, emulada em arm64), e o
#    dump SQL não depende de arquitetura
geonode-docker stop db
podman run -d --name pgmig15 --platform linux/amd64 -v $P-dbdata:/var/lib/postgresql/data \
  -v $P-dbbackups:/pg_backups docker.io/geonode/postgis:15-3.5-latest
podman exec pgmig15 pg_dumpall -U postgres -f /pg_backups/migracao-pg15-para-pg17.sql
podman rm -f pgmig15
# 3. volume novo no 17 (o geonode.sh da imagem cria os papéis e os bancos vazios) e restore
geonode-docker rm -f db && podman volume rm $P-dbdata
geonode-docker up -d db
geonode-docker exec db psql -U postgres -d postgres -q -f /pg_backups/migracao-pg15-para-pg17.sql
```

No restore, os erros "already exists" de papéis, bancos e dos schemas `topology` e `tiger` são esperados, porque a imagem nova já os cria. Depois do restore, compare as contagens de tabelas e de `base_resourcebase` com as do banco antigo. O PostGIS cai de 3.5 para 3.4 (`CREATE EXTENSION` não fixa a versão). Isso não afetou os dados do ambiente de desenvolvimento, migrado assim em 23/11/2026. O dump fica no volume `dbbackups` e contém os hashes de senha dos papéis: apague-o, junto com o volume de backup, depois de validar a migração.

## Problemas conhecidos (pendentes nas dependências)

- **[mapstore-client]** **Caixas "Publicado" e "Aprovado" não aparecem no painel de configurações do recurso (`DetailsSettings`).** Em `client/js/utils/ResourceUtils.js`, `RESOURCE_PUBLISHING_PROPERTIES` e `RESOURCE_OPTIONS_PROPERTIES` são constantes calculadas no carregamento do módulo (`filterResourcePublishingProperties()`). Elas leem `getConfigProp('geoNodeSettings').isPublishedOptionEnabled` e `isApprovedOptionEnabled` antes de o client carregar a configuração da página, então `is_published` e `is_approved` são sempre removidos, mesmo com `RESOURCE_PUBLISHING=True` e `ADMIN_MODERATE_UPLOADS=True` e com o usuário admin. O problema existe na 5.0.3 instalada e continua na `master` e no `5.0.x` upstream; não há issue aberta.
  - **Correção prevista:** trocar as constantes por funções avaliadas no uso, em `DetailsSettings.jsx`, `epics/gnsave.js` e `selectors/resource.js`. Não dá para contornar no opengeosgb, porque o cálculo acontece no carregamento do bundle. Até lá, aprovar e publicar pelo admin do Django ou pela API (`PATCH /api/v2/resources/<pk>`).
  - **Admin do Django:** `opengeosgb/admin.py` substitui os admins de Dataset, Map, Document e GeoApp (este último cobre dashboards e GeoStories). Ele acrescenta as ações em lote Aprovar, Publicar, Aprovar e publicar, Despublicar e Reprovar. Quando `is_approved` ou `is_published` mudam, seja pelas ações ou pela edição na lista ou no formulário, o recurso é salvo com `save(notify=True)`, com os campos `was_*` sincronizados com o banco. O save padrão do admin (`notify=False`) só gravaria os campos, sem atualizar as permissões do fluxo, as regras do GeoFence e as notificações. Com `ADMIN_MODERATE_UPLOADS` e `RESOURCE_PUBLISHING` ativos, aprovar e publicar concede `view` e `download` ao usuário anônimo.
